# PokéLife (reboot)

**`docs/pokelife/` is the source of truth** for what PokéLife is and what to build (owner, 6 November 2026): start at `docs/pokelife/README.md`, then the Product Bible and the module or feature spec you are touching. `docs/design.md`, `docs/ecosystem.md` and `docs/economy.md` describe what the code does today and are evidence, not authority; where they disagree with `docs/pokelife/`, it wins, and a rule changes in the owning `docs/pokelife/` file first. Decisions already made there: Android is the only product platform (desktop and web are dev conveniences that gate nothing); local-only has priority (no new Supabase, account or sync work; they are retired after the migration gates); the modules are PLAN, CARE, HEAL, MINT, HOME, LINK, GEAR and WORLD (no Grow, no Explore); one currency, Poké; and a Pokémon in **one place only** (7 November 2026): the global buddy (the main companion, cosmetic), a party of one lead and five per module (its bonuses apply to that module only), a Guardian slot, a WORLD expedition team, a GEAR helper (visual only), or the PC (`Places` in app-core; every assignment takes the Pokémon from its old place). `docs/pokelife/IMPLEMENTATION_BACKLOG.md` is the work list.

The app is **PokéLife** (renamed from PokéPlan in 0.47.0; PokéPlan is now the name of its Plan module). Code packages (`app.pokeplan.*`), the repository, the Android application id and the save keep the old name. A fun productivity, growth and self-improvement app for Pokémon lovers: finishing a focus timer hatches an Egg, finishing tasks, habits and goals earns candies and items that level up and evolve Pokémon. The repo holds two codebases:

- **The rewrite (repo root):** Kotlin Multiplatform (Android, desktop, web), local-only (the Supabase backend was retired in 0.130.0). `docs/pokelife/` says what to build; `docs/design.md` records the game rules the code implements today. Read the relevant `docs/pokelife/` spec before changing game rules, and update it (and `docs/design.md` when the code changes) when a rule changes. Numbers marked *(tune)* there are starting values.
- **The original app (`legacy-android/`):** a native Android Java app from a MOBDEVE pair project, kept as the reference for the old rules. It is no longer developed.

## Layout
**Detail for every line below is in `docs/code-map.md`: grep it for the module before touching one (storage tables, schema numbers, sealing, key classes).**
- Rule modules (Kotlin Multiplatform, JVM and wasmJs, no UI): `pokemon-core/` (Dex, reward engine, owned Pokémon; knows nothing about tasks), `plan-core/` (focus, tasks, recurrence, goals, review), `care-core/`, `heal-core/`, `mint-core/` (exact integer money), `home-core/`, `link-core/`, `world-core/` (docs/world.md). A life module knows nothing about Pokémon or rewards: its store in `app-core` pays through the `World` interface with a minimal event (`CareEvent`, `HealEvent`, `MintEvent`, `HomeEvent`, `LinkEvent`) that never carries a figure, a name or a private word.
- `app-core/`: the rules engine with no UI. `GameStore` applies every user action and saves one `AppData` through a `Storage`; each life module has its own store (`CareStore`, `HealStore`, `MintStore`, `HomeStore`, `LinkStore`). Tests: `./gradlew :app-core:jvmTest`.
- `data/`: the local SQLite database (SQLDelight, Android and JVM only), live on Android since 0.129.0. `LiveDocuments` splits the save into per-module tables (`plan_*`, `care_*`, `heal_*`, `mint_*`, `home_*`, `link_*`, the Pokémon, Bag and ledger tables) and puts it back together on a read. **A schema change needs a numbered `.sqm` migration and the released schema committed in `databases/N.db`. Heal and Mint rows and every backup of them are sealed (AES-256-GCM, Android Keystore) and fail closed without the key: never write them unsealed, never log them.** Desktop and web keep JSON stores. Tests: `./gradlew :data:jvmTest`.
- `composeApp/`: the shared Compose UI (`app.pokeplan.ui`; `App()` is the entry; screens in `screens/`, the theme and house components in `theme/`). The bottom tabs are Home / Modules / Pokémon / Me; a tab or module with several sections opens on a menu of cards (`screens/Menu.kt`), not tab pills. `ScreenshotTest` renders screens to `composeApp/build/screenshots/*.png` (`./gradlew :composeApp:jvmTest`).
- `androidApp/`: the thin Android application (reminders through `reminders/SharedReminders.kt`, Glance widgets in `widgets/`, the database wiring in `LiveStore.kt`). Widgets and the app share one save; the app calls `GameStore.reload()` when it comes back to the front.
- **No cloud (0.130.0):** no Supabase, accounts, sync or server; rewards are decided on the phone. Do not add any.
- `assets/`: real game assets, listed with sources and licences in `docs/assets.md`; how each is fetched is in the `game-assets` skill. `legacy-android/`: the old Java app, see the `legacy-android` skill.
- Docs: `docs/pokelife/` (authority), `docs/design.md` (rules the code implements), `docs/economy.md` (every reward source, sink and cap, under `RewardRules.VERSION`: bump it, and update that file, with any rule that changes what an event pays).
- The buddy never chats: no permanent speech bubble, needs or mood meter; level and progress sit small in a corner, and one reaction (like a game emote) happens only for a real event or a tap (`GameStore.buddyEvent()`, an egg hatched or a payout in the last few minutes, celebrated once): a Mystery Dungeon status icon for a tap (`ReactionIcon`: a sparkle, a flame for a Fire type, a heart...; no emoji), its SpriteCollab portrait for an event. It sleeps during focus and hops or eats with its own SpriteCollab animations (`SpriteAction`); `Portrait` and `SpeakerBox` show its face beside text.
- `DayBackground` (composeApp) is the default page behind every screen (`AppBackdrop` swaps in a real scene or dungeon town under a veil when Settings → Look → Background asks): an ordered-dither gradient with a light grain, drawn in code as UI chrome (not art) and tinted by the time of day; screens must not paint their own opaque background over it.
- **Art rule (owner's): use real game assets only (PokeAPI/sprites, Showdown) and the PMD SpriteCollab sprites, which are the preferred Pokémon sprites (CC BY-NC 4.0: non-commercial, credit the artists); never hand-draw, generate or procedurally draw pixel art.** UI chrome (panels, buttons, bars) is drawn in code; icons and sprites are always real assets.
- **Versioning:** `VERSION` at the repo root (`MAJOR.MINOR.PATCH`, below 1.0 a feature bumps the minor and a fix the patch) is the single source. Gradle turns it into the Android `versionName` and the generated `AppVersion` shown in Settings → About; the release workflow also passes its run number as `POKEPLAN_BUILD` (the Android `versionCode` and "build N"; without it the app says "dev"). `release-apk.yml` publishes the rolling "Latest build" and, the first time a `VERSION` is seen, that version's own `vX.Y.Z` release. Bump `VERSION` in the PR that ships something and add it to `CHANGELOG.md`.
- Signing: every build (local and CI) uses the committed `androidApp/pokeplan-debug.keystore` (alias `pokeplan`, password `pokeplan`), SHA-1 `1A:28:99:CD:34:46:02:04:1E:AF:7B:15:7F:D1:07:41:BC:30:F0:A5`, so the app signature is stable. Private repo only; TODO before any public release: move to a secret key.

## Commands (rewrite, from the repo root)
- All tests (JVM): `./gradlew jvmTest`; one module: `./gradlew :pokemon-core:jvmTest`; one class: `./gradlew :pokemon-core:jvmTest --tests "app.pokeplan.core.EggTest"`
- Compile the web target: `./gradlew compileKotlinWasmJs` (wasm tests need yarn and a browser and are not run here)
- Regenerate Dex data: `python3 -I tools/species/generate.py`
- The golden vector (`pokemon-core/src/jvmTest/resources/golden.json`, checked by `GoldenVectorTest`): regenerate with `UPDATE_GOLDEN=1 ./gradlew :pokemon-core:jvmTest --tests "*GoldenVectorTest*"` after a deliberate rule change (and bump `RewardRules.VERSION`).
- **Actions are used sparingly (owner's rule, 6 November 2026):** `ci.yml` runs on a PR only with the `ci`, `android` or `apk` label (or by hand); `release-apk.yml` skips merges that change only docs, notes or `legacy-android/`. The local `./gradlew jvmTest compileKotlinWasmJs` is the normal gate. Apply `ci` to a PR only when its change really needs the runner.
- CI (`.github/workflows/ci.yml`) runs, when asked for as above, on a PR that changes more than text (a PR touching only `docs/`, `.md` files, `.claude/` or `legacy-android/` is not tested), and only there (not again on `main` after a merge; a newer push to a PR cancels the older run), as one job to save Actions minutes: the cheap checks first (VERSION, regenerating the Dex data changes nothing), then the JVM tests and the wasm build, then the Android app is **compiled** only when the PR touches `androidApp/`, an `androidMain` source set or the Gradle files (or has the `android` label). An APK is packaged, and kept as an artifact for 3 days, only for a PR with the `apk` label. It shares its Gradle cache key with the release workflow, so a PR starts from the last merge's downloads (check the "Cache" lines of a run to see whether that works).
- `.github/workflows/release-apk.yml` publishes every merge to `main` as the "latest" GitHub release with `pokeplan.apk` (debug build, shared signing key), so the newest app can be installed from a phone.
- World economy simulation: `./gradlew :world-core:simulateWorldEconomy` writes `docs/world-economy-report.md` (floors, jobs, facilities, Café, Swap Shop, Dojo, shop over a year); re-run it after changing any World number.
- Economy simulation: `./gradlew :plan-core:simulateEconomy` writes `docs/economy-report.md` (about 1 to 2 minutes). Re-run it after changing any reward, rank, egg, candy or transfer number and compare with the pacing targets in docs/design.md.
- Android app: `./gradlew :androidApp:assembleDebug` (APK in `androidApp/build/outputs/apk/debug/`). Desktop: `./gradlew :composeApp:run`. Web: `./gradlew :composeApp:wasmJsBrowserDevelopmentRun`. Compile checks without a display: `./gradlew :composeApp:compileKotlinJvm :composeApp:compileKotlinWasmJs`.
- Gradle 9.8.1, Kotlin 2.4.21, AGP 9.4.1, Compose Multiplatform 1.12.2, any JDK 17 to 21.
- In the cloud sandbox: `dl.google.com` (Google's Maven and the Android SDK) must be in the environment's allowed domains. The SessionStart hook (`.claude/hooks/session-start.sh`, cloud sessions only, no tokens spent, runs in the background) installs the SDK to `~/android-sdk` (cmdline-tools, `platform-tools`, `platforms;android-37.0`, `build-tools;37.0.0`), writes `local.properties`, and adds a Gradle init script in `~/.gradle/init.d` that tries `https://maven-central.storage-download.googleapis.com/maven2` first, because Maven Central rate-limits the shared proxy. **Before the first Gradle command of a cloud session, run `.claude/hooks/wait-for-setup.sh`**: it returns at once when the hook is done, waits while it runs, and says so if it failed (then run the hook by hand: `CLAUDE_CODE_REMOTE=true .claude/hooks/session-start.sh`). PokeAPI data and sprites are reachable through `raw.githubusercontent.com` (not `pokeapi.co`).

## Design rules (owner's, 8 November 2026)
Read `docs/pokelife/FEATURES/DESIGN_SYSTEM.md` sections 5.1 and 12A before any UI change. In short: every big section sits in a dialogue box; every control is pixel-drawn with stair corners (`PixelField`, `PixelToggle`, `PixelSlider`, `PixelBar`; no Material rounded parts); module colours follow the rainbow table (Pokégear on top, World at the bottom, red is not chrome); the buddy shows on Home only; a row's contents share one centre line; and no caption that restates what is on the screen (empty states are a title and one action, menu cards an icon and a title). Look at a real screenshot in both palettes before calling a screen done.

## Swarm workflow and token use
- For a large task, plan first, then split it. Simple subtasks (reading files, searches, formatting, quick checks) go to Haiku sub-agents (`model: "haiku"`); moderate ones (routine code edits, drafting, a test for an existing rule) to Sonnet sub-agents (`model: "sonnet"`). Planning, game-rule and economy decisions, and the final review stay in the main session at high effort. Small tasks are done directly, with no sub-agents.
- Sub-agents start cold: give each a self-contained prompt (files, goal, what to return). Run independent ones in parallel. Ask for short reports (the answer, not file dumps), and check their output before reporting it as done.
- Search before reading, and read only the line ranges you need (`offset` and `limit`).
- Never read these whole: `pokemon-core/src/commonMain/resources/dex/*.json` (generated, about 900 KB in all: grep the species or form), `docs/design.md` (about 50 KB: grep its headings, then read that section), everything under `docs/pokelife/` (about 700 KB: read `README.md` and the Product Bible, then grep headings and read one section), `docs/ecosystem.md`, `docs/ui-ux-brief.md`, `docs/code-map.md`, `docs/region-candidates.md`, `kotlin-js-store/yarn.lock`, and `CHANGELOG.md` beyond its newest entry. Never list `assets/sprites`, `assets/animated`, `assets/pmd` or `assets/cries` (thousands of files); grep their `.tsv` manifests.
- Images cost tokens: open a `ScreenshotTest` PNG or a sprite only for the screen or Pokémon you changed, never a whole folder.
- Gradle output is long: run builds and tests with `--console=plain` and trim to what matters, e.g. `./gradlew jvmTest --console=plain 2>&1 | grep -E "FAILED|BUILD|e: |Test.*>" | head -40`. Re-run only the failing module or class (`--tests`). Run the slow ones (`simulateEconomy`, `assembleDebug`, the wasm build) only when the change needs them, in the background where you can.
- Send broad searches (where is X used, which screens show Y) to an Explore or Haiku agent. Leave `legacy-android/` alone unless the task is about it.
- Keep replies short and skip restating the diff.

## Parallel sessions (the owner runs several at once)
Sessions start from "continue with the next chunk", so two can pick the same one (LINK was built twice, 7 to 8 November 2026). The session-start hook prints what other sessions have pushed and not merged (`.claude/hooks/in-flight.sh`, last 3 days, with each branch's first commit, the folders it touches and its `VERSION`). Run it again by hand any time; `in-flight.sh <word>` filters.
- **Pick** the first backlog item (`docs/pokelife/IMPLEMENTATION_BACKLOG.md`, then the guide's order) that no in-flight branch or recent merge on `main` already covers. When in doubt, read that branch's commits (`git log origin/<branch> --not origin/main`) before starting.
- **Claim it as your first action**, before reading code: `.claude/hooks/claim.sh "<backlog id> <topic>"` checks the other branches for the same words (exit 2: pick another), then pushes an empty `claim: ...` commit on your session branch so every other session sees it. `FORCE=1` only for a chunk that is really different. If you drop the chunk or find it done elsewhere: `claim.sh --release "why"`.
- **Re-check before the PR:** `git fetch origin main`, run `in-flight.sh` again, and merge `main` in. If `main` or another branch now has the same work, stop and say so instead of merging a duplicate; port only what is missing. Two branches with the same `VERSION` collide: take the next free number after fetching, just before the PR.
- Touching a file many sessions edit (`CHANGELOG.md`, `IMPLEMENTATION_*`, `GameStore.kt`, `App.kt`)? Merge `main` in early and often; add your lines at the end of a section so conflicts stay trivial.

## Working rules (from the 12 November 2026 session review)
- **Asking the owner for a decision:** write each question as a standalone item: what it is (the screen or feature, in plain words, no shorthand from earlier in the session), why it matters in one sentence, two or three lettered options, and your recommendation. Number them so one reply ("1A 2C") answers all. For one the owner leaves unanswered, use the recommendation and say so in the PR body under "Defaults applied". Gather every open question into one list before building, not one at a time.
- **The test gate is slow (about 14 minutes):** while working run only the targeted tests (`:module:jvmTest --tests ...`, `:composeApp:compileKotlinJvm`); run the full `./gradlew jvmTest compileKotlinWasmJs` once, on the merged head, just before the PR. While it runs in the background, draft the PR body and re-read the diff; do not poll. Trust the run you started last: a Monitor notice from an older run is stale, so check it against the current run before acting on it.
- **"Merge" means all of it:** commit, push, fetch `main` and merge it in (take the next free `VERSION` and changelog slot, and prefer `main`'s version of a feature both sides built), run the gate, open the PR, merge it once it is clean (see Branches and pull requests), then say what merged. Do not stop after the push, and if something blocks the merge, say exactly what.
- **Keep PRs scoped (owner's one-PR-per-session rule still holds):** inside the one branch, commit per item, and split off a separate PR only for something risky or urgent, as that rule says; a small urgent fix (a visible bug) is such a case and should not wait for the rest.

## Sessions and handoff
- One session per topic (a roadmap item, or a batch of fixes from phone testing). Start a new session rather than continuing a long one: every turn resends the whole conversation, so a long session costs more for each step.
- When the topic is done (its PRs merged, or open and green), Claude ends with a **handoff prompt** the owner pastes into the next session: what shipped (PR numbers), what is still open and its state, decisions waiting on the owner (deploys, merges), and the next item with where its spec lives. It does not repeat what this file, the skills or the docs already say.
- `docs/pokelife/IMPLEMENTATION_BACKLOG.md` and `CHANGELOG.md` are the record of progress: keep them current, so a new session needs nothing else.

## Branches and pull requests
- `main` is the stable branch. Don't push to it directly (the one exception is the first "Initial commit"): every change reaches it through a pull request.
- **Every change starts a new branch from the latest `main`** (`git fetch origin main && git checkout -b <name> origin/main`), even a one-word fix. **One PR per session (owner's rule, 6 November 2026): bundle everything a session does, several backlog items included, into one branch and one PR, and run the full local gate and merge once at the end, not after each item.** Commit per item inside the branch so the history stays readable. Split off a separate PR only for a change the owner may want to revert on its own (a risky migration, a store cutover) or one that cannot wait for the rest. Never reuse a branch whose PR is merged or closed (a cloud session's own branch is the one exception, below).
- **Branch names:** `<type>/<area>-<topic>`, lowercase, words joined with hyphens, the topic 1 to 4 words. It must match `^(feat|fix|content|design|chore|docs)/(auth|home|focus|tasks|pokedex|party|settings|data|ui|build|repo|care|heal|mint|link|gear|world)-[a-z0-9]+(-[a-z0-9]+)*$`.
  - Types: `feat` (new behaviour or screen), `fix` (something broken), `content` (Pokédex entries, FAQ text, rarity and reward tables, strings), `design` (layouts, styles, drawables), `chore` (dependencies, Gradle, cleanup), `docs` (CLAUDE.md, README, comments).
  - Areas: `auth` (the starter pick and first run), `home`, `focus` (timer, eggs, Deep Focus), `tasks` (planner, reminders, candy rewards), `pokedex`, `party` (party, PC, levelling, evolution), `settings` (settings and profile), `data` (the stores in `app-core/` and the database in `data/`), `ui` (shared widgets and navigation), `build` (Gradle, CI), `care`, `heal`, `mint`, `link`, `gear` and `world` (that module), `repo` (everything else). A change that touches several areas but serves one takes that area; otherwise `ui` or `repo`.
  - Examples: `fix/focus-deep-focus-threshold`, `content/pokedex-gen-three`, `feat/tasks-recurring-reminders`, `chore/build-upgrade-agp`.
- **Claude sessions:** a cloud session is handed its own branch (`ccr-…`, `claude/…`) and may push only there, so it works on that branch (`claim.sh` and `in-flight.sh` already assume it) and the naming rule above applies to branches made by hand. If its PR is already merged, restart the same branch from the latest `main`. Never push to `main`.
- **After the changes, open a PR** into `main`: bring in the latest `main` first, run `./gradlew jvmTest compileKotlinWasmJs` from the repo root (and `testDebugUnitTest assembleDebug` from `legacy-android/` only if you touched it), and read the diff once more. Title: `<type>(<area>): <what changed>`, sentence case, no final period, e.g. `fix(focus): Reset the timer when the screen turns off`. **Once CI is green on the PR's latest commit and it has no merge conflict, Claude merges it (a merge commit)** (the owner's standing rule; the cloud sandbox cannot delete remote branches, so GitHub's "Automatically delete head branches" setting or the owner removes them); while CI is red because of the PR, Claude fixes it first. **If CI is red only for a failure that is not in the PR's change (the same check is red on `main` or on other PRs, or a test that passes locally fails on the runner) and `./gradlew jvmTest compileKotlinWasmJs` passes locally, Claude merges anyway** (the owner's rule, November 2026), after one comment on the PR saying which check and why it is not the PR's.
- **If GitHub Actions cannot run because of billing** (the checks fail to start or the run says the account is locked or payments failed, not a red test), CI is not a gate: run `./gradlew jvmTest compileKotlinWasmJs` locally instead, merge the PR once those pass and it has no conflict, and **end the session by building the APK by hand with a build number**, since `release-apk.yml` will not run. Use `POKEPLAN_BUILD=<N> ./gradlew :androidApp:assembleDebug`, where N is one more than the build in the title of the newest "Latest build (vX.Y.Z, build N)" release (`list_releases`), and send `androidApp/build/outputs/apk/debug/` `*.apk` to the owner with `SendUserFile`, saying the version and build number. The handoff prompt says Actions was down, so the owner knows the release was not published and the next build number may need correcting.
