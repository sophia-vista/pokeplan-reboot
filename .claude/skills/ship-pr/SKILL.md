# Shipping a PR

The owner's rules, moved here verbatim from CLAUDE.md (13 November 2026 token trim). CLAUDE.md keeps a short summary; this file is the full text.

## Branches and pull requests
- `main` is the stable branch. Don't push to it directly (the one exception is the first "Initial commit"): every change reaches it through a pull request.
- **Every change starts a new branch from the latest `main`** (`git fetch origin main && git checkout -b <name> origin/main`), even a one-word fix. **One PR per session (owner's rule, 6 November 2026): bundle everything a session does, several backlog items included, into one branch and one PR, and run the full local gate and merge once at the end, not after each item.** Commit per item inside the branch so the history stays readable. Split off a separate PR only for a change the owner may want to revert on its own (a risky migration, a store cutover) or one that cannot wait for the rest. Never reuse a branch whose PR is merged or closed (a cloud session's own branch is the one exception, below).
- **Branch names:** `<type>/<area>-<topic>`, lowercase, words joined with hyphens, the topic 1 to 4 words. It must match `^(feat|fix|content|design|chore|docs)/(auth|home|focus|tasks|pokedex|party|settings|data|ui|build|repo|care|heal|mint|link|gear|world)-[a-z0-9]+(-[a-z0-9]+)*$`.
  - Types: `feat` (new behaviour or screen), `fix` (something broken), `content` (Pokédex entries, FAQ text, rarity and reward tables, strings), `design` (layouts, styles, drawables), `chore` (dependencies, Gradle, cleanup), `docs` (CLAUDE.md, README, comments).
  - Areas: `auth` (the starter pick and first run), `home`, `focus` (timer, eggs, Deep Focus), `tasks` (planner, reminders, candy rewards), `pokedex`, `party` (party, PC, levelling, evolution), `settings` (settings and profile), `data` (the stores in `app-core/` and the database in `data/`), `ui` (shared widgets and navigation), `build` (Gradle, CI), `care`, `heal`, `mint`, `link`, `gear` and `world` (that module), `repo` (everything else). A change that touches several areas but serves one takes that area; otherwise `ui` or `repo`.
  - Examples: `fix/focus-deep-focus-threshold`, `content/pokedex-gen-three`, `feat/tasks-recurring-reminders`, `chore/build-upgrade-agp`.
- **Claude sessions:** a cloud session is handed its own branch (`ccr-…`, `claude/…`) and may push only there, so it works on that branch (`claim.sh` and `in-flight.sh` already assume it) and the naming rule above applies to branches made by hand. If its PR is already merged, restart the same branch from the latest `main`. Never push to `main`.
- **After the changes, open a PR** into `main`: bring in the latest `main` first, run `./gradlew jvmTest compileKotlinWasmJs` from the repo root (and `testDebugUnitTest assembleDebug` from `legacy-android/` only if you touched it), and read the diff once more. Title: `<type>(<area>): <what changed>`, sentence case, no final period, e.g. `fix(focus): Reset the timer when the screen turns off`. **Once CI is green on the PR's latest commit and it has no merge conflict, Claude merges it (a merge commit)** (the owner's standing rule; the cloud sandbox cannot delete remote branches, so GitHub's "Automatically delete head branches" setting or the owner removes them); while CI is red because of the PR, Claude fixes it first. **If CI is red only for a failure that is not in the PR's change (the same check is red on `main` or on other PRs, or a test that passes locally fails on the runner) and `./gradlew jvmTest compileKotlinWasmJs` passes locally, Claude merges anyway** (the owner's rule, November 2026), after one comment on the PR saying which check and why it is not the PR's.
- **If GitHub Actions cannot run because of billing** (the checks fail to start or the run says the account is locked or payments failed, not a red test), CI is not a gate: run `./gradlew jvmTest compileKotlinWasmJs` locally instead, merge the PR once those pass and it has no conflict, and **end the session by building the APK by hand with a build number**, since `release-apk.yml` will not run. Use `POKEPLAN_BUILD=<N> ./gradlew :androidApp:assembleDebug`, where N is one more than the build in the title of the newest "Latest build (vX.Y.Z, build N)" release (`list_releases`), and send `androidApp/build/outputs/apk/debug/` `*.apk` to the owner with `SendUserFile`, saying the version and build number. The handoff prompt says Actions was down, so the owner knows the release was not published and the next build number may need correcting.

## The gate, merging, scope (working rules from the 12 November 2026 session review)
- **The test gate:** `./gradlew jvmTest compileKotlinWasmJs` takes a few minutes since it skips the screenshots (all of them took about 12 more; `-Pscreenshots` renders them, CI does). While working run only the targeted tests (`:module:jvmTest --tests ...`, `:composeApp:compileKotlinJvm`); run the full `./gradlew jvmTest compileKotlinWasmJs` once, on the merged head, just before the PR. While it runs in the background, draft the PR body and re-read the diff; do not poll. Trust the run you started last: a Monitor notice from an older run is stale, so check it against the current run before acting on it.
- **"Merge" means all of it:** commit, push, fetch `main` and merge it in (take the next free `VERSION` and changelog slot, and prefer `main`'s version of a feature both sides built), run the gate, open the PR, merge it once it is clean (see Branches and pull requests), then say what merged. Do not stop after the push, and if something blocks the merge, say exactly what.
- **Keep PRs scoped (owner's one-PR-per-session rule still holds):** inside the one branch, commit per item, and split off a separate PR only for something risky or urgent, as that rule says; a small urgent fix (a visible bug) is such a case and should not wait for the rest.

## CI and Actions
- **Actions are used sparingly (owner's rule, 6 November 2026):** `ci.yml` runs on a PR only with the `ci`, `android` or `apk` label (or by hand); `release-apk.yml` skips merges that change only docs, notes or `legacy-android/`. The local `./gradlew jvmTest compileKotlinWasmJs` is the normal gate. Apply `ci` to a PR only when its change really needs the runner.
- CI (`.github/workflows/ci.yml`) runs, when asked for as above, on a PR that changes more than text (a PR touching only `docs/`, `.md` files, `.claude/` or `legacy-android/` is not tested), and only there (not again on `main` after a merge; a newer push to a PR cancels the older run), as one job to save Actions minutes: the cheap checks first (VERSION, regenerating the Dex data changes nothing), then the JVM tests and the wasm build, then the Android app is **compiled** only when the PR touches `androidApp/`, an `androidMain` source set or the Gradle files (or has the `android` label). An APK is packaged, and kept as an artifact for 3 days, only for a PR with the `apk` label. It shares its Gradle cache key with the release workflow, so a PR starts from the last merge's downloads (check the "Cache" lines of a run to see whether that works).
- `.github/workflows/release-apk.yml` publishes every merge to `main` as the "latest" GitHub release with `pokeplan.apk` (debug build, shared signing key), so the newest app can be installed from a phone.
