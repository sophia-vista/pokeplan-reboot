# Code map

Where everything lives and what each module's storage looks like. `CLAUDE.md` holds the short version and the rules; this file holds
the detail that used to sit in its Layout section (moved here on 11 November 2026 so it is not loaded into every session).
**Grep this file for the module you are about to touch; do not read it whole.** Update it in the same change as the code it describes.
Decisions, rules and constraints that the code alone does not show live in `docs/decisions/` (one page per module, grouped by source file; they used to be code comments, moved there in the 21 November 2026 comment audit).

- `pokemon-core/`: the Pokémon side, reusable by every module (see "Platform and modules" in docs/design.md); Kotlin Multiplatform (JVM and wasmJs), no UI, knows nothing about tasks or focus. Packages under `app.pokeplan.core`: `dex` (the National Dex: species, forms, evolutions, regional dexes, Pokédex text, types, rarity, egg rarity tables and hatch rules; the Dex tables are the generated JSON files `src/commonMain/resources/dex/*.json`, read by `DexParser`; the JVM and Android read them as resources and the web build gets them built into its code by `generateDexWebSources`), `reward` (the reward engine, candy reward tables, trainer rank), and `pokemon` (an owned Pokémon with IVs, EVs, nature, ability, gender, shiny, friendship; stat formula; hatching; items (including `Items.megaStones`, one Mega Stone per Mega form, Primal Kyogre and Groudon as the Blue and Red Orb), bag, perks and transfer; candy, friendship and shiny rules; evolution rules; and the Guardian role of legendaries and mythicals in `Perks.kt`). `jvmMain/tools` holds JVM-only reports such as `./gradlew :pokemon-core:curationReport`.
- **Package layout (owner's modular rule):** every module's code sits in its own package in each layer. `composeApp/.../ui/`: `plan/`, `care/`, `heal/`, `mint/`, `base/`, `link/`, `world/`, `gear/` (screens and logic), `pokemon/` (the Pokémon tab, PC, Pokédex, Bag, Mart, party and perks), `launcher/`, `theme/`, and `screens/` for what every module shares (Home, Me, Settings, Menu, Components, Modules, onboarding, tutorials). `app-core/.../app/`: `base/`, `care/`, `heal/` (with the Huawei Health parsing), `link/`, `mint/`, `world/` (alerts and `WorldActions.kt`), `gear/` (`GearActions.kt`: helpers, timers), `plan/` (nudges, task links), `reminders/`, `storage/`, `quest/`; the package root keeps `GameStore`, `AppData` and what several modules share. World and Gear actions are extension functions on `GameStore` (import them from their package). `androidApp/`: `platform/` (sensors, torch, haptics, files, phone state), `health/`, `reminders/`, `widgets/`, `launcher/`, `huawei/`; the classes the manifest names stay in the root package.

- `care-core/`: the Care module's rules (routines, calm breaks, mood check-ins, prompts, trends; package `app.pokeplan.care`), JVM and wasmJs; its screens are `care/Care.kt` (five places from the Sections key: Today, Routines, Calm, Reflect, Dream) and `care/CareDream.kt` (the Dream place, was CareMeadow.kt) (Modules → Care, `AppModel.care`). It meets the game only through `CareEvent` (`RewardEngine.care`); `CareStore` in app-core keeps its own save and pays through the `World` interface (docs/pokelife/FEATURES/POKEMON_ECOSYSTEM.md).

- `data/`: the local SQLite database (docs/pokelife `ARCHITECTURE/DATA_AND_MIGRATIONS.md`, REP-008): SQLDelight on SQLite, Android and JVM targets only, package `app.pokeplan.data`. Schema in `src/commonMain/sqldelight/.../Data.sq`; every released schema is committed in `databases/N.db`, and `jvmTest` runs `verifyCommonMainDataDbMigration`, so a schema change needs a numbered `.sqm` migration. `DataStore` (foreign keys checked on open, one transaction coordinator), `PokemonRepository`, `EconomyRepository` (idempotent, append-only ledger). **Live on Android:** the app's two JSON documents (`save`, `care`) live in the table `live_document` (`LiveDocuments`, schema v2), activated once from `save.json` and `care.json` (which are then never written again, kept as the rollback copy), with a daily file backup of the documents (`LiveBackup`, `filesDir/backups/`, newest 3) and a move-aside-and-restore path for a corrupt file; the Android wiring is `androidApp/.../LiveStore.kt` behind `saveStorage()`/`careStorage()`. The normalized tables (Pokémon, Bag, ledger) are the live authority for the player's side of the save (below); desktop and web keep their JSON stores. The shared reminder feature stores its snoozes and repeats in `reminder_hold` (schema v3). **PLAN's records live in their own tables (schema v5):** `PlanTables` under `LiveDocuments`, which splits the `save` document into PLAN's part (`plan_*` tables) and the rest (the `save` row) and puts it back together on a read; `movePlanToTables` activates it once with read-back. **Care's records live in their own tables (schema v4, REP-014):** `CareTables` takes the Care JSON apart into `care_*` rows and puts it back together under the unchanged `CareStore`, and `LiveDocuments` routes the `care` document through them after `moveCareToTables` (read back, old row kept aside); **The shared Pokémon, Bag and ledger tables are live (schema 6, REP-014):** `PokemonTables` splits the player's part of the `save` document (the Pokémon, their places, the Dex history, the Egg meter and trainer points, the Bag and the Poké balance) from the rest, `movePokemonToTables` activates it once (the save first goes through `GameStore.normalizeDocument`, which `LiveStore` sets as `LiveDocuments.normalizer`; read-back compared, the old save kept as `aside:save:pokemon:<millis>`, the balances one opening-balance event), a Pokémon's place is at most one row of `pokemon_place` (primary key = the Pokémon; WORLD teams and GEAR helpers stay in the `save` row and the write refuses a Pokémon named there and in the table), the ledger is the only writer of the balance and the Bag (a live write settles the change of one save as one event), and `WorldData.poke` is never stored. The app still reads one `AppData` through the split; the typed repositories are not used by it yet (`DATA_AND_MIGRATIONS.md` section 7.3.0). HEAL, MINT, BASE and LINK are on their own tables too (schemas 7 to 10; 11 adds `heal_steps`/`heal_vital`, 12 `home_room`); next: the typed repositories per module and the backup archive (`docs/pokelife/IMPLEMENTATION_GUIDE.md` section 3.2). Tests: `./gradlew :data:jvmTest`.
